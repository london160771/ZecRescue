## Phase 5 — Production hardening

**Status:** Implementation and local tests are present; Phase 5 acceptance is pending Phase 3 completion and integrated verification. Mainnet deployment and production reimbursement calibration are deliberately not claimed.

- **Implementation:** Added a minimal `RescueRouter` that uses Circle `receiveWithAuthorization` plus a second owner-signed, chain/router-specific EIP-712 route consent. The contract has no owner, upgrade, arbitrary call, or sweep. The server verifies router code hash/token/TTL, quote and signature bindings, both nonce states, exact simulation, minimum rescue amount, configured reimbursement and gas ceilings, and a 2x relayer balance reserve. ## Phase 3 source/API blocker correction — 2026-10-19

- **Finding:** Official Zingolib v7.0.0 and current `dev` do not implement the safe operation required by ZecRescue. `LightWallet::create_shield_proposal` is crate-private, gathers every transparent receiver in the wallet, and sets the shield output to `ShieldedPool::Orchard`; `LightClient::propose_shield` only wraps that method. The CLI reports only amount/fee. The separate `zcash_client_backend::data_api::wallet::propose_shielding` function does accept an explicit `from_addrs` slice, but Zingolib does not connect that API call to its private stored-proposal and signing/transmission lifecycle.
- **Consensus consequence:** NU6.3/Ironwood activated on Mainnet at height 3,428,143; Orchard is restricted. The stock `shield` and `quickshield` commands are not acceptable for Recovery Vault shielding.
- **Decision:** Do not create more accounts or wallet directories. Keep the existing agent shield endpoint blocked. A custom Zingolib fork/upstream API is a possible engineering route, but no current supported integration was proven, and no local bridge was implemented or built. This is the Phase 3 blocker and meets the stop condition for unavailable safe wallet APIs.
